# CLAUDE.md: Wanderer's Guild

Foundry VTT module (v13 minimum, verified v14 build 370; dnd5e 6.x, verified 6.0.6): professions built on dnd5e tool proficiencies. A character has every profession whose linked tool it is proficient with (no limit); the rank is its proficiency bonus, named by a GM-editable rank table that also gives the highest craftable rarity. 0.1.0 = slice 1 (definitions, ranks, Professions window, setup window); 0.2.0 = slice 2 (recipes, crafting rules as world data, the Crafting window, leader-made crafts); 0.3.0 = slice 3 (gathering: nodes, scene tiers, harvesting, leader-given resources) and the Professions page on the toolkit's sheet; 0.3.2 = audit fixes (player days capped, used-roll list, roll verification, debounced Gather redraws, tooltip test); 0.3.3 = effect dice bonuses accepted in roll verification; 0.4.0 = recipe discovery and learning (Learned by, recipe items, Teach to…, Show/Hide unknown recipes, learn card and hook); 0.5.0 = craft outcomes and batches (better result margin + per-recipe better result, batch crafting). Logic only; campaign content stays in each world. Public repo, MIT. Built on **wanderers-core 0.6.0** (vendored; never edit `vendor/` by hand: `node vendor/wanderers-core/vendor.mjs update X.Y.Z`, behind the proxy with `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt`; core's CONVENTIONS.md applies).

## Data
- World settings (every client reads them, so nothing GM-only): `professionList` `{ v: 1, list: [{ id, name, kind, tools[], icon, check, actions[], notes }] }`, `rankTable` `{ v: 1, rows: [{ bonus, name, rarity }] }`, `recipeBook` `{ v: 3, list: [{ id, name, profession, group, result: { uuid, name, img, type, rarity, price: { value, denomination } | null, qty }, rarity ("" item's / "none" / key), materials: [{ uuid, name, img, qty }], dc, hours, cost (gp) | null, auto, learn ("rank" | "item" | "gm"; v1 reads as rank), better: { qty, uuid, name, img, type, rarity } (0.5; v2 reads as none = qty 0, uuid ""), notes }] }`, `craftRules` `{ v: 2, timeHours, timePerGp, rounding, hoursPerDay, materialPct, byRarity: { <rarity>: { hours, cost, dc } }, consumablePct, dc, helpersMax, helperDivides, failMaterials, chargeCoin, rankTime: { <bonus>: pct }, betterMargin (0.5, null = off), batchMax (0.5, null = off; 2..BATCH_LIMIT 50) }` (v1 reads with both null), `gatherRules` `{ v: 1, tiers: [{ id, name, dc }], rareMargin, qty, qtyMode ("perDay" | "flat"), reach, crBands: [{ cr, dc }], creatures: [{ type, profession, item, rare, minBonus }], areas: [{ profession, tier, item, rare }] }` (item refs `{ uuid, name, img }`), `gatherReset` `{ v: 2, at, days }` (`days` = the last toolkit journey's length, null after a GM reset; v1 reads with null), `showUnlearned`, `playersLearn`, `undiscoveredRecipes` (choice show | hide, 0.4; display only), `craftApproval`, `worldCoins`, `gatherOnce`, `gatherArea`, `gatherJourney`, `debugLog`, the feature switches. Professions carry `roll` ("skill" | "tool", 0.3, no version bump: missing = skill). Client: core's `windowPlacement` (keys `professions`, `setup`, `crafting`, `gather`; never rename).
- **No rulebook figures ship.** `defaultRules()` is all null / neutral (100 %, 0 helpers, failMaterials "lose" (user decision: consumed on use), no charge); a test checks it and the rules page's inputs start empty. Never add a default number to the rules, a rank perk, or a recipe.
- Actors: `flags.wanderers-guild.recipes` `{ v: 1, ids }` (known recipes; written only in craft-leader.mjs).
- Recipe items (0.4): `flags.wanderers-guild.teaches` `{ v: 1, recipe, consume }` on items (world items by the GM in learn-gm.mjs; copies carry it). Learn cards `flags.wanderers-guild.learn` `{ v: 1, actor, recipe, source, at }`. Hook `wanderers-guild.learned` `{ actorId, recipeId, source }`. A character's professions and rank are still derived on every draw from prepared data: `system.tools[key].prof.multiplier` (fallback `.value`; 0 / 0.5 / 1 / 2), `system.attributes.prof`, `system.details.level`. Learned = multiplier ≥ 1 with any linked tool; no linked tool = everyone (but crafting needs a linked tool to roll). Rank = the table row with the highest bonus ≤ PB; it crafts rarities up to its row's `rarity`; mundane ("") needs none.
- Gathering (0.3): scene `flags.wanderers-guild.tier` (Table Tools field, saved by the scene form); nodes = core Notes with `flags.wanderers-guild.node` `{ v: 1, profession, name, item, rare, tier, dc, qty, uses, minBonus, hidden, resetAt }` (no journal entry; `hidden` is an honor system: Notes reach every client); actor `flags.wanderers-guild.gathered` `{ v: 1, marks: [{ key: n:<scene>.<note> | s:<scene>, at }] }` (a mark counts while newer than both `gatherReset.at` and the node's `resetAt`; marks are written for every resolved check, uses spent on successes); token `flags.wanderers-guild.harvested` `{ v: 2, list: [{ actor, profession, at }] }` (once per creature **per profession**, ≤ `HARVEST_MAX` 10; v1 `{ actor, profession, at }` reads as a one-entry list; written with `withHarvest`); gather cards `flags.wanderers-guild.gather` `{ v: 1, state, actor, profession, kind, target, total, dc, rare, at }`; rolls carry `gatherRoll { actor, profession, target }` (target = node / token UUID or `scene:<id>`) and `rollUsed`.
- Chat: craft cards `flags.wanderers-guild.craft` `{ v: 1, state: pending|done|failed|refused|error, actor (uuid), recipe, user, roll, tool, total, dc, helpers, batch (0.5, missing = 1), betterAt, better, whisper, approval, timeText, at }` (additive, no card version bump), notices `flags.wanderers-guild.notice`; tool check rolls carry `flags.wanderers-guild.craftRoll { actor, recipe }` (set by the crafter's client through dnd5e's message data) and `rollUsed` (leader).
- GM-only data (later: hidden recipes, GM notes) never goes in a world setting or a flag players can see: use core `createStore` (Module data journal) as the toolkit's `vault.mjs` does, with a cap per bucket and cleanup.

## Key patterns
- **Feature registry:** a turned-off tool registers nothing (no hooks, buttons, menus, key bindings, socket handlers); its API getter returns undefined. Gate registration with `F.on("<id>")`.
- **Settings keys are stable** across versions (never rename). A new setting is a row in `S`; visible switches use `tab: "settings"` (the setup window's Settings page lists bool rows of that tab). A new record goes in `S` with `hidden: true` (it lands in `RECORDS`, skipped by the Satchel's export).
- **GM edits are direct** (a GM click writes the world setting through `data.mjs`, after the model's normalizer). **Actor writes** (known recipes, crafted items, materials, coin) happen only in `craft-leader.mjs` handlers (and `economy.mjs` `pay`, called from them), which core runs on `leader.isLeader()`; players and GM tabs send `leader.request(kind, data)` with a schema in `REQUESTS`, and the handler checks Foundry's sender user's rights (owns the actor), never a payload user id, then re-runs `assess()`. Gathering writes live in `gather-leader.mjs` the same way. GM-click Note writes (nodes) only in `nodes.mjs` and `cleanup.mjs` (test: their embedded writes are "Note" only). GM-click world-item flag writes (recipe items) only in `learn-gm.mjs` (test). Tests: writes only in those files, no `data.user`, no `game.socket`.
- **Learning (0.4, user decisions, binding)**: no NPC trainers (no trainer flag, request or reach; recipes for coin are recipe items sold like any item). Routes per recipe: Rank (players learn it, as before), Recipe item (only an item or a GM), GM only; default Rank. Rank applies to items too (above-rank items stay, "needs <rank>"). `learnFromItem` `{ actor, item }`: sender owns the actor, `LM.itemOnActor(item, actor.uuid)`, the leader re-reads the item's stored `teaches` flag (never a recipe id from the payload), `assessLearn`, learns, then `useUpPlan` (lower / delete unless keep), all inside `serial(actor)`. Every learn posts the learn card (asking user, the actor's players, GMs) and fires the hook. *Teach to…* = `learnRecipe` per actor from the GM. *Recipes not known yet* Hide is display only (say so in hint and README). No skill-ups.
- **Crafting roll**: rolled on the crafter's client (`actor.rollToolCheck({ tool, target: dc }, {}, { data: { flags } })`, dnd5e 6.0.6: the message is `rolls[0].parent`); the request sends the message id, never a total. The leader reads the total from the message (`readRoll`: author = sender, our `craftRoll` flag matches, `ROLL_MAX_AGE_MS`, not `rollUsed`), marks it used (the flag and the leader's `USED` list, `usedRolls`), checks a player's roll with `verifyRoll` (GM rolls trusted; unverifiable → whispered refusal, or with `craftApproval` the pending card with "Roll not checked: …"), then resolves at once (user decision): materials from the inventory are consumed on success and, unless `failMaterials` is "keep", on failure; no DC anywhere → success (card: "no DC set: crafted"). Only `craftApproval` (default off) makes a pending card (GM + crafter) whose buttons send `craftDecide`; the leader re-assesses at approval. Not craftable at resolve (materials or coin gone, …) → a `refused` card, nothing consumed. Crafts per actor run one at a time (`serial` in craft-leader.mjs). The window tells the player what will be used up before rolling (`usesNotice`, next to Craft and as its tooltip); no confirm dialog.
- **Better results and batches (0.5, user-approved scope)**: both off by default (`betterMargin` / `batchMax` null; never ship a number). Better = success && DC set && margin set && the recipe `hasBetter` && total ≥ DC + margin (`assess().betterAt`, `isBetter`); it makes `resultPlan(recipe, { batch, better })`: the better item (if `uuid`) instead of the normal one, quantity (result.qty + better.qty) × batch. Batch: `craft` request `qty` (optional int 1–`BATCH_LIMIT`), the leader `clampBatch(data.qty ?? 1, rules)` (only ever lowers) and re-assesses with it; one roll; `assess` multiplies materials (`need` = each × batch), hours (before rounding), cost and charge; `consumePlan(inv, materials, a.batch)`; failure spends the batch per `failMaterials`. The leader never reads a better result or a total from the payload. No skill-ups, no trainers.
- **Gathering decisions (user, binding)**: scene tiers only, no tier on core Regions (don't add one). Harvesting is once per creature per profession. Quantity: one check per journey stage; `qtyMode` "perDay" (default) gives `qty` × days (nodes and areas; creatures and "flat" ignore days; rare replaces one of the total); days come from the Gather window's *Days in this stage* (1–30, prefilled from `gatherReset.days`, which the journey listener sets from the payload's `hours` as max(1, ceil(hours / 24))) and travel in the `gather` request (`days`, integer 1–30, required); the leader applies `allowedDays` (a player can't exceed the last journey's days; 1 with none), and the window shows players the same cap. Area gathering needs the character's token on the scene (GMs excepted). No book figures.
- **Gathering roll**: same pattern as crafting: `rollSkill({ skill, target })` or `rollToolCheck({ tool, target })` on the gatherer's client with `gatherRoll` in the message flags; request `gather` with exactly one of node / scene / token (plus `days`); the leader's `readRoll` (author, flag match, age, unused by flag and `USED`) then `assessGather` again from `gatherFacts`, then `verifyRoll` for a player's roll (refused with the reason; no approval escape) (reach uses the actor's token on the target's scene; GMs skip reach and token checks). No approval step. A harvest also runs serially per token (`serial("token:<uuid>")`) so two professions' marks don't overwrite each other. Toolkit journey (`wayfarersToolkit.journey`, GM client only; only `hours` read, through `daysFromHours`) → `resetGatherLimits(days)` on the leader, else relayed with `gatherReset { days? }`.
- **Time is FYI**: never call `game.time.advance` or write world time (test).
- **Prices**: `economy.mjs` only; book = `BOOK_VALUES` + core `coins(…, { ratio: 10 })`; world (`worldCoins` + toolkit active) = `CONFIG.DND5E.currencies` values, the toolkit's `moneyHTML` and `pay(actor, amount, { reason })`.
- **Hot hooks** (`updateActor`, item and effect hooks) bail first unless a Professions / Crafting window is open for that actor and the change touches its `ACTOR_PATHS` (or a class/background/species/feat item, or an effect; the Crafting window redraws on any item change, since items are materials). `renderChatMessageHTML` bails unless the message has our `craft` flag. Gather windows: HP / `controlToken` / `targetToken` go through `refreshSoon()` (100 ms `foundry.utils.debounce`, bails with no window open).
- **Tooltips**: Foundry's TooltipManager (v13/v14) renders `data-tooltip` and `data-tooltip-html` as HTML after the attribute is decoded; `data-tooltip-text` is plain text. Document text (names, notes) only in `title` or `data-tooltip-text`; `data-tooltip` only with fixed module text (repo test).
- **Roll honesty limits** (README *Rolls and honesty*): the dice faces (d20 and bonus dice) and advantage/disadvantage are not verifiable; situational bonuses, dice typed in the dialog, proficiency dice and a changed ability are refused for players; dice bonuses on the character for that check (0.3.3) are accepted.
- **Windows**: ApplicationV2 via core `RememberedWindow`, classes `wg-window` + `...UI_CLASSES` (test; never a literal `wc-r<N>`). The setup window uses core's shell and components (`wc-pagehead`, `wc-panel`, `wc-table`, `wc-btn`, `wc-alert`); the Professions window has its own dark palette on `.wg-prof` (tokens `--wg-*`), the same in both themes. Pages are pure strings; `setup.mjs` routes `data-action` in `_onClickAction`; Enter/Space on the sidebar never reach Foundry (Space pauses).
- **Health check** never throws, never changes anything, GM only (players `[]`); a line's fix runs only on a GM click after its confirm. Contract as the toolkit's `healthReport`: `run({ timeoutMs })` → `[{ title, lines: [{ level, text, fix? }] }]`.
- **Cleanup covers everything we write:** `cleanup.mjs` `plan()` / `remove()` / `CATEGORIES` (`professions`, `ranks`, `recipes`, `rules`, `known` (the `recipes` actor flag only), `recipeItems` (the `teaches` flag on world and carried items; items stay), `gathering` (rules, reset record, scene tiers), `nodes` (Notes deleted), `gathered` (actor flag, world actors and unlinked tokens' actors), `harvested` (token flag), `cards` (our craft / learn / gather cards and notices deleted, roll marks unset), `settings` incl. client `windowPlacement`). Flags are removed per key (`unsetKey`), so categories don't touch each other. A new flag, setting, document or folder must be added there.
- **Toolkit integration**: read only through `game.modules.get("wayfarers-toolkit")?.api` (`coinRatio()`, `moneyHTML()`, `pay(…, { reason })`), in `economy.mjs`, defensively, never required. Toolkit sheet page (`api.sheet.registerPage`, toolkit 2.3.0; feature `toolkitPage`): one guest page per client; the guest contract applies (no `data-action` / `data-name` / `[data-drop]` in the page: `data-wg-act`; HTML escaped by us; never write toolkit data). Buttons in the window and the page both go through `Professions.runAction(actor, act, data)`.
- **Docs:** README *Public API and hooks* lists every `api.*` entry and hook, stable or experimental; docs/professions.md is the user guide. Update both with any change.

## Release process
1. Bump `version` in `module.json` and `package.json`, and the `download` URL (`.../releases/download/vX.Y.Z/module.zip`); the manifest URL stays `https://github.com/cocoomg11/wanderers-guild/releases/latest/download/module.json`.
2. Add a `CHANGELOG.md` section (`## X.Y.Z`; the release workflow checks it) with an "Untested in Foundry" checklist.
3. Commit and push to main. **Agents never tag or publish.** The user publishes the GitHub release with a tag `vMAJOR.MINOR.PATCH` only; the Release workflow (read-only build job, then an upload job) checks the tag, the changelog, the core pin (`verify --remote`), runs the checks and uploads `module.json` + `module.zip` (`module.json scripts styles lang vendor README.md CHANGELOG.md LICENSE`, minus `vendor/wanderers-core/config/`, `testing/` and `vendor.mjs`). A new top-level folder must be added to the zip step.
4. Keep `compatibility` honest (minimum 13, verified = newest build checked live, no maximum) and the dnd5e `relationships.systems` entry (minimum 6.0.0, verified = last checked live). Optional modules (wayfarers-toolkit, item-piles) in `relationships.recommends`, never `requires`.
