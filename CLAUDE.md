# CLAUDE.md: Wanderer's Guild

Foundry VTT module (v13 minimum, verified v14 build 370; dnd5e 6.x, verified 6.0.6): professions built on dnd5e tool proficiencies. A character has every profession whose linked tool it is proficient with (no limit); the rank is its proficiency bonus, named by a GM-editable rank table that also gives the highest craftable rarity. 0.1.0 = slice 1 (definitions, ranks, Professions window, setup window); 0.2.0 = slice 2 (recipes, crafting rules as world data, the Crafting window, leader-made crafts); gathering (slice 3) is a placeholder. Logic only; campaign content stays in each world. Public repo, MIT. Built on **wanderers-core 0.6.0** (vendored; never edit `vendor/` by hand: `node vendor/wanderers-core/vendor.mjs update X.Y.Z`, behind the proxy with `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt`; core's CONVENTIONS.md applies).

## File map (`scripts/`)
- `main.mjs` entry: settings (`init`), hooks and buttons gated by `F.on(...)`, the API (`game.modules.get("wanderers-guild").api`, set in `init`), `leader.start()` in `ready`, the Satchel registration, hook `wanderers-guild.ready`.
- `const.mjs` module id, title, hook names, `TOOLKIT_ID`, `SYSTEM_ID`; re-exports `esc`/`plural` from core. The id lives only here (and module.json).
- `core.mjs` the one place core is bound: `F` (features `professions`, `sheetButton` and `crafting` need professions), `S` (settings rows), `RECORDS`, `changed` (listeners run on every client when the definitions, ranks, recipes, rules or switches change), `log`/`warn`, `REQUESTS` (`learnRecipe`, `forgetRecipe` gm, `craft`, `craftDecide` gm) and `leader`.
- `professions-model.mjs` (pure) definitions: `normalizeProfessions` (v1, `PROFESSIONS_MAX` 100, `TOOLS_MAX` 8), `cleanProfession`, `upsert`/`remove`/`move`, `KINDS`, `ACTIONS`, `KIND_ACTIONS`, `ICONS` (original stroke paths), `STARTER` + `addStarter`, `professionWarnings`.
- `ranks-model.mjs` (pure) rank table: `normalizeRanks` (v1, `RANKS_MAX` 12, sorted, one row per bonus, never empty), `DEFAULT_ROWS`, `RARITIES` (dnd5e keys), `rankFor`, `ladder`, `nextRankText`, `bonusAtLevel` / `levelForBonus` (SRD 5.2 proficiency bonus table), `rankWarnings`, `signed`.
- `character-model.mjs` (pure) a character's professions from plain facts: `characterProfessions`, `professionsView` (cards / others / unlearned), `profMark`, `checkText`.

- `dnd5e.mjs` every dnd5e read (tool/skill/rarity labels, `facts(actor)` from prepared data; 0.2: `inventory(actor)`, `coinValues()`, `toolTotal`, `typeLabel`, `itemSnapshot`). `data.mjs` the GM's setting writes (`saveProfessions`, `saveRanks`, `addStarterSet`, `saveRecipes`, `saveRules`) and reads (`recipes()`, `rules()`, `known(actor)`).
- `recipes-model.mjs` (pure, 0.2) recipes `normalizeRecipes` (v1, `RECIPES_MAX` 300, `MATERIALS_MAX` 12), `cleanRecipe`, `recipeRarity`, `upsertRecipe`/`removeRecipe`/`mergeRecipes`, export/`readRecipesImport`, `recipeWarnings`; known recipes `normalizeKnown` (v1, `KNOWN_MAX` 200), `learn`/`forget`/`knows`.

## Data
- World settings (every client reads them, so nothing GM-only): `professionList` `{ v: 1, list: [{ id, name, kind, tools[], icon, check, actions[], notes }] }`, `rankTable` `{ v: 1, rows: [{ bonus, name, rarity }] }`, `recipeBook` `{ v: 1, list: [{ id, name, profession, group, result: { uuid, name, img, type, rarity, price: { value, denomination } | null, qty }, rarity ("" item's / "none" / key), materials: [{ uuid, name, img, qty }], dc, hours, cost (gp) | null, auto, notes }] }`, `craftRules` `{ v: 1, timeHours, timePerGp, rounding, hoursPerDay, materialPct, byRarity: { <rarity>: { hours, cost, dc } }, consumablePct, dc, helpersMax, helperDivides, failMaterials, chargeCoin, rankTime: { <bonus>: pct } }`, `showUnlearned`, `playersLearn`, `craftApproval`, `worldCoins`, `debugLog`, the feature switches. Client: core's `windowPlacement` (keys `professions`, `setup`, `crafting`; never rename).
- **No rulebook figures ship.** `defaultRules()` is all null / neutral (100 %, 0 helpers, failMaterials "lose" (user decision: consumed on use), no charge); a test checks it and the rules page's inputs start empty. Never add a default number to the rules, a rank perk, or a recipe.
- Actors: `flags.wanderers-guild.recipes` `{ v: 1, ids }` (known recipes; written only in craft-leader.mjs). A character's professions and rank are still derived on every draw from prepared data: `system.tools[key].prof.multiplier` (fallback `.value`; 0 / 0.5 / 1 / 2), `system.attributes.prof`, `system.details.level`. Learned = multiplier ≥ 1 with any linked tool; no linked tool = everyone (but crafting needs a linked tool to roll). Rank = the table row with the highest bonus ≤ PB; it crafts rarities up to its row's `rarity`; mundane ("") needs none.
- Chat: craft cards `flags.wanderers-guild.craft` `{ v: 1, state: pending|done|failed|refused|error, actor (uuid), recipe, user, roll, tool, total, dc, helpers, whisper, approval, timeText, at }`, notices `flags.wanderers-guild.notice`; tool check rolls carry `flags.wanderers-guild.craftRoll { actor, recipe }` (set by the crafter's client through dnd5e's message data) and `rollUsed` (leader).
- GM-only data (later: hidden recipes, GM notes) never goes in a world setting or a flag players can see: use core `createStore` (Module data journal) as the toolkit's `vault.mjs` does, with a cap per bucket and cleanup.

## Key patterns
- **Feature registry:** a turned-off tool registers nothing (no hooks, buttons, menus, key bindings, socket handlers); its API getter returns undefined. Gate registration with `F.on("<id>")`.
- **Settings keys are stable** across versions (never rename). A new setting is a row in `S`; visible switches use `tab: "settings"` (the setup window's Settings page lists bool rows of that tab). A new record goes in `S` with `hidden: true` (it lands in `RECORDS`, skipped by the Satchel's export).
- **GM edits are direct** (a GM click writes the world setting through `data.mjs`, after the model's normalizer). **Actor writes** (known recipes, crafted items, materials, coin) happen only in `craft-leader.mjs` handlers (and `economy.mjs` `pay`, called from them), which core runs on `leader.isLeader()`; players and GM tabs send `leader.request(kind, data)` with a schema in `REQUESTS`, and the handler checks Foundry's sender user's rights (owns the actor), never a payload user id, then re-runs `assess()`. Tests: writes only in those files, no `data.user`, no `game.socket`.
- **Crafting roll**: rolled on the crafter's client (`actor.rollToolCheck({ tool, target: dc }, {}, { data: { flags } })`, dnd5e 6.0.6: the message is `rolls[0].parent`); the request sends the message id, never a total. The leader reads the total from the message (`readRoll`: author = sender, our `craftRoll` flag matches, `ROLL_MAX_AGE_MS`, not `rollUsed`), marks it used, then resolves at once (user decision): materials from the inventory are consumed on success and, unless `failMaterials` is "keep", on failure; no DC anywhere → success (card: "no DC set: crafted"). Only `craftApproval` (default off) makes a pending card (GM + crafter) whose buttons send `craftDecide`; the leader re-assesses at approval. Not craftable at resolve (materials or coin gone, …) → a `refused` card, nothing consumed. Crafts per actor run one at a time (`serial` in craft-leader.mjs). The window tells the player what will be used up before rolling (`usesNotice`, next to Craft and as its tooltip); no confirm dialog.
- **Time is FYI**: never call `game.time.advance` or write world time (test).
- **Prices**: `economy.mjs` only; book = `BOOK_VALUES` + core `coins(…, { ratio: 10 })`; world (`worldCoins` + toolkit active) = `CONFIG.DND5E.currencies` values, the toolkit's `moneyHTML` and `pay(actor, amount, { reason })`.
- **Hot hooks** (`updateActor`, item and effect hooks) bail first unless a Professions / Crafting window is open for that actor and the change touches its `ACTOR_PATHS` (or a class/background/species/feat item, or an effect; the Crafting window redraws on any item change, since items are materials). `renderChatMessageHTML` bails unless the message has our `craft` flag.
- **Windows**: ApplicationV2 via core `RememberedWindow`, classes `wg-window` + `...UI_CLASSES` (test; never a literal `wc-r<N>`). The setup window uses core's shell and components (`wc-pagehead`, `wc-panel`, `wc-table`, `wc-btn`, `wc-alert`); the Professions window has its own dark palette on `.wg-prof` (tokens `--wg-*`), the same in both themes. Pages are pure strings; `setup.mjs` routes `data-action` in `_onClickAction`; Enter/Space on the sidebar never reach Foundry (Space pauses).
- **Health check** never throws, never changes anything, GM only (players `[]`); a line's fix runs only on a GM click after its confirm. Contract as the toolkit's `healthReport`: `run({ timeoutMs })` → `[{ title, lines: [{ level, text, fix? }] }]`.
- **Cleanup covers everything we write:** `cleanup.mjs` `plan()` / `remove()` / `CATEGORIES` (`professions`, `ranks`, `recipes`, `rules`, `known` (actor flags), `cards` (our cards and notices deleted, roll marks unset), `settings` incl. client `windowPlacement`). A new flag, setting, document or folder must be added there.
- **Toolkit integration**: read only through `game.modules.get("wayfarers-toolkit")?.api` (`coinRatio()`, `moneyHTML()`, `pay(…, { reason })`), in `economy.mjs`, defensively, never required. Toolkit sheet page (`api.sheet.registerPage`, toolkit 2.3.0): not wired yet; the Crafting pages are pure strings (`crafting-view.mjs`) so a sheet page can host them later.
- **Docs:** README *Public API and hooks* lists every `api.*` entry and hook, stable or experimental; docs/professions.md is the user guide. Update both with any change.

## Release process
1. Bump `version` in `module.json` and `package.json`, and the `download` URL (`.../releases/download/vX.Y.Z/module.zip`); the manifest URL stays `https://github.com/cocoomg11/wanderers-guild/releases/latest/download/module.json`.
2. Add a `CHANGELOG.md` section (`## X.Y.Z`; the release workflow checks it) with an "Untested in Foundry" checklist.
3. Commit and push to main. **Agents never tag or publish.** The user publishes the GitHub release with a tag `vMAJOR.MINOR.PATCH` only; the Release workflow (read-only build job, then an upload job) checks the tag, the changelog, the core pin (`verify --remote`), runs the checks and uploads `module.json` + `module.zip` (`module.json scripts styles lang vendor README.md CHANGELOG.md LICENSE`, minus `vendor/wanderers-core/config/`, `testing/` and `vendor.mjs`). A new top-level folder must be added to the zip step.
4. Keep `compatibility` honest (minimum 13, verified = newest build checked live, no maximum) and the dnd5e `relationships.systems` entry (minimum 6.0.0, verified = last checked live). Optional modules (wayfarers-toolkit, item-piles) in `relationships.recommends`, never `requires`.

## Rules
- Public repo: no campaign names, no game-publisher wording or setting names in user-facing text, code, tests or defaults; no private details (IPs, domains, local paths). Generic wording ("classic MMO" at most). Default rank names stay neutral (Novice, Apprentice, Adept, Expert, Master).
- No official non-SRD rules text or figures. The 2024 crafting time and cost tables are not SRD: never ship them; every number is world data with neutral or SRD 5.2 defaults (SRD 5.2: proficiency bonus by level, item rarities). Never use 5etools or other unofficial rules sites. Verify Foundry APIs at foundryvtt.com/api and dnd5e at github.com/foundryvtt/dnd5e; do not guess an API.
- Every feature toggleable; strings plain English in code (`lang/en.json` stays empty). No macros on hotbars.
- Commit author `cocoomg11 <cocoomg11@users.noreply.github.com>`; end commit messages with the attribution trailers given by the session.
- Another agent may be committing to main: `git fetch origin main` and rebase before pushing.
